### 仕様の読み方と衝突時の優先順位

1. **ユーザーからの最新の明示指示・確定要件**。本工程表を渡すことでCodex実装開始が承認された場合も、確認を取るべき権限境界は別。
2. [SPEC.md](../../SPEC.md) の**確定仕様**。次に分野別資料（戦闘、敵、階層、スキル、アイテム等）の確定部分。
3. **この工程ファイルは「今どこまで実装するか」を決める**。全機能を1工程で実装しろ、とは読まない。
4. 数値の仮案は試遊／シミュレーションに基づき変更可。ただし確定仕様と混同せず、変更理由を残す。
5. [UIモック](../UI_MOCKS.md)は**デザイン参考**。画像内の数値や死亡時アイテム持ち帰り等は仕様確定ではない。
6. 旧[HTML試作](../../prototype/index.html)は**最新仕様に非対応**。再利用してもよいが、そのまま移植する義務はない。

**矛盾を見つけたら**、確定仕様を隠れて変更せず、仮対応を明記する。例：階層台帳に人間加入イベントEV03があるが、工程1は主人公単独なので**工程1だけ候補から除外・再抽選**し、工程2以降に本来の意味で実装。ドキュメントの未着手表記は工程が実際に始まった時に更新する。

## 各工程の共通完了条件

- [ ] 指示範囲だけを実装し、先行実装した未承認の機能がない。
- [ ] 本体の実動作・自動テスト・ヘッドレス検証・Windows EXE/ZIPの状態を報告。
- [ ] 実際のゲーム画面を撮影し、該当するモックと比較できる（不可能なら理由と代替検証）。
- [ ] AIによる自己レビューと少なくとも1回の改善／再テストを実施。
- [ ] [PROGRESS.md](PROGRESS.md) と [IMPLEMENTATION_STATUS.md](../IMPLEMENTATION_STATUS.md) をエビデンス付きで更新。
- [ ] PR・コミット・CI・配布物の参照先、既知の未解決点が残っている。

**工程の詳細指示に記載された追加条件を優先**。工程1から進め、途中で仕様を勝手に決めすぎない。
