# 大量建築・複数選択の性能監査（2026-10-14）

ソース変更とheadlessロジック検査のみ。EXEは配布済みcaf02f8のまま。実画面・GPU・人間の操作感は未検証。過去のPC全体のフリーズとは別に、今回のCPUロジック遅延を再現した。

## 原因と根拠

基準はブランチcodex/sporehollow-biome01の8e3a1e8。既存の診断F9、比較シェーダー、診断起動スクリプトは撤去済みで、復活させていない。既存のterrain_metricsをheadlessテスト中だけ有効化し、回数を集計した。通常OFF、画面表示・常時記録・ファイル書き込み機能は追加していない。

- `Buildings.reason`は1候補ごとに`rooms()`を呼び、100候補で100回／679,900セルを訪問。確定時はプレビューと予約で200回／1,359,800セルを訪問した。
- `WallStroke.plan`は同じドラッグ内容にも全候補を再検証。100セルを3回再評価すると2,039,700セルを訪問した。
- 100仕事・10人の選択では、既に他人へ割当済みの分を除く955候補に対して屋内探索955回／6,493,045セル。A*も955回／101,989展開。建築判定が主因だが、経路探索も無視できない。
- 選択ドラッグは候補一覧の再生成・全件ソートに加え、既遭遇の配列内検索を各候補で実施。確定時の比較関数も配列findを繰り返していた。
- `draw_work_plans`に全仕事の状態文言を毎回作る処理は現在ない。ただし地形・仕事等を巨大な文字列へ変換する署名は、経路を表示しない時にも作成していた。右上キュー非表示は維持。

## 実装

- 屋内判定：建設で囲まれる可能性のある屋外専用動物の連結領域だけを調べる。床のないセルまたは外周への開口を見つければ屋外確定。完成済みの壁・ドアのみを境界とし、床・像の敷地、開いたドアの屋内維持を従来どおり扱う。予約・着工・施工中／完成前の検査を省略しない。
- ドラッグ：世界状態が同じ間は評価結果を再利用し、新しく追加したセルだけ評価。停止中の変更も構造物・床・動物・物資等のキーで検出。確定時はキャッシュを使わず全対象を再確認する。
- 予約索引：同期したプレビュー／確定の処理内で、座標＋仕事種類、座標＋建築層の辞書を1回作り、追加時に更新する。次の操作では現在の仕事から再構築するため取消・完了・別機能からの追加を取りこぼさない。永続的な索引を古いまま保持しない。100件／101件目拒否を維持。
- 仕事選択：24件以上かつ閉じたドアによる経路重みがない場合、同じ住人の1回の評価内で到達距離を段階的に広げて再利用する。目標セルの優先順・仕事優先度・待機加点・ID同点処理を維持。小件数や閉ドアありは従来A*と同じ評価で、同一目標の距離だけ再利用する。計算は同期評価内で完結し、次の住人／tick／地形変更へキャッシュを持ち越さない。実歩行の占有回避処理は変更しない。
- 選択：静的候補の生成・距離順ソートを変更時だけ行う。動物の画面上位置は毎回取得。静的候補と少数の動的候補を順序を保って結合し、範囲内の未遭遇候補だけを記録。遭遇順位を辞書化し、確定時の線形findを廃止。8対象上限と入力確定・右クリック取消の経路は維持。
- 描画準備：非表示経路は準備自体を省略。未割当だけの時も経路計算不要。必要時は文字列の代わりに状態のhashを比較。画面外の仕事マーカーを除外する（複数の誘導先を持つ命令は保守的に除外しない）。

## 測定条件

100×68、seed731、同一の空地・住人配置・10×10内の建築候補。建設の材料待ちと組立評価を分離するため、この負荷試験は無限素材fixture。実在物資の運搬・消費は別の既存integration試験で確認した。住人の仕事選択は1→5→10人の順次1回ずつ。30fps制限付きheadless・Dummy音声・低CPU優先度・直列。数値は処理関数の経過時間で、FPSやGPU時間ではない。呼出回数の計測コストを含み、OS負荷にも左右される。通常のWorld.step全体、全地形／全端末の最悪値を示すものではない。

変更前後の33標本ずつは[before.json](before.json)／[after.json](after.json)。全量の再測定を無目的に繰り返さず、長ドラッグのみ同条件で3回比較した。

- 単独A*を100目標×10人で直接呼ぶ比較：2806.12 → 2907.43ms。展開104,290回は同一。A*本体は改善しておらず、ここは誤差範囲の変動として扱う。

## 計算量と拡張性

N=マップセル数、J=仕事数、B=ドラッグセル数、H=住人数、A=屋外専用動物数、R=対象動物の領域の探索セル数、C=選択候補数、D=ドラッグ更新回数、S=状態キーを作るデータ量。

|処理|変更前|変更後・限界|
|---|---|---|
|候補の屋内検査|O(B×N)|通常O(B×A×R)。未舗装上の動物ならR=1。全域舗装などの最悪R=Nは残る|
|同じドラッグ再評価|O(B×N)|O(S)。変更時O(S＋追加セルの検査)。キーhashも完全に無料ではない|
|一括予約の重複検査|O(B×J＋B²)|処理開始O(J)、照会・追加は平均O(1)、一括O(J＋B)。単発APIを別々に100回呼ぶ経路は毎回索引を作る|
|仕事距離評価|住人ごと候補数分A*|単位コスト経路は各セル最大1展開／評価、O(H×(N＋J log J))が上限の目安。閉ドア時は従来A*|
|既存A*|線形frontier探索・contains・pop_atで最悪O(N²)|本体は維持。距離評価内で呼出数を減らしたのみ|
|選択|毎更新O(C log C)、遭遇判定に最大O(C²)、確定ソート中にもfind|静的変更時O(C log C)、通常更新O(S＋C＋動物ソート)、遭遇照会平均O(1)。空間索引は未導入|
|非表示経路の準備|全状態の文字列生成＋必要時経路|O(1)で終了。表示中は依然O(S)のhashと必要時経路|

6,800セルしかなくても旧処理はB/J/Hを掛けて繰り返すため秒単位に増加していた。今回の初回プレビュー・確定は候補数におおむね比例。人を増やした仕事選択も依然増える。マップ寸法そのものを変える測定は依頼どおり実施せず100×68固定。マップ拡大時の記載は静的な計算量評価である。

## 正確性・安全性

- [correctness.json](correctness.json)：299項目。全マップ屋内判定との固定seed比較、最後の壁／床、開いたドア、停止中の移動／樹木追加、確定時再検査、100件と101件、取消／完了後再予約、閉ドア／迂回路を含む旧経路距離と仕事ID比較、選択候補の変化。
- [integration.json](integration.json)：既存30項目。現物の回収・搬入・組立、運搬担当と建築担当の協力、徴兵中断、取消後の数量、役割優先度。既存のデータ変換用一時fixture検査を含むが、ゲームへセーブ機能を戻していない。
- 計測は生成済みのモデルとデータ準備のみ。ゲームシーンを画面へ出さず、Windows入力やGPU試験はなし。通常EXEハッシュはBFD152F5E5EC0A465C0BA35550A25F1D68F161E3C83DD335FEE3125B21CE668Fで変更なし。
- 既存素材・通常データ・他の未保存import変更を保全。一時試験フォルダ・生成キャッシュは既存工程で片付けた。新しいEXEは作っていない。

## 残課題・推奨順

1. **10人同時評価は約115ms**。60fpsの1フレーム内には収まらない。住人の評価をフレーム予算で分散する設計、優先度変更／対象消失／危険対応時の即時再評価を組み合わせる必要がある。今回はAI応答順を無断変更しないため未導入。
2. 閉じたドア・長い迂回・到達不能を含むA*の優先キュー化。重み・同点順を保った同値検証が必要。実歩行は占有回避もあるため仕事評価の距離表を流用していない。
3. 大量の床と犬の組合せでは局所探索も広がる。完成地形の連結成分と局所変更差分を共有する方式を検討。完成時の正確な拒否判定は維持する。
4. 永続的な仕事索引・地形版番号を導入するなら、各所のjobs.append/eraseや地形直接変更を一つの変更APIへ集約する必要がある。今回は安全な同期トランザクション内へ限定した。単発予約・Delivery.job・Work.activeの線形検索は残る。
5. 選択カタログと経路署名のhashは更新ごとにO(S)。数万オブジェクトでは空間バケットと変更通知が必要。主描画のscene_actors全体生成、状態パネルのwork_summary、物流の候補ごとのStock検索も後続の監査対象。
6. 資材不足時のDelivery.proposal、閉ドアが多数ある町、遠距離／迷路、1,000仕事（現行上限外）は今回の負荷表では測っていない。一般条件の最悪時間は未確定。
7. 実GPUのマーカー欠け・赤線・入力の体感は未確認。今回の成果でPC全体フリーズが解消したとは判断しない。EXE更新・実画面検査は別途指示を受けて行う。

再現コマンド：`./dev.ps1 test -Suites scale_correctness,drag_scale,scale_logic`、物流は `-Suites integrated_work`。build/play/visualは今回実行禁止。旧候補生成の参照コードはtests配下で、export対象外。
