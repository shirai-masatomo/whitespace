## 2. FPS・バックグラウンド・内部時間

- `project.godot` に `application/run/max_fps` の明示設定なし。`game/`に `Engine.max_fps` の設定なし。`tools/launch_current.ps1` もFPS指定なし。**現在の起動経路で60fps上限は保証されていない。**実効FPSは未測定で、VSync等によって変わり得る。
- `main.gd:1562` のフォーカス喪失処理はキー／ドラッグ状態の解除のみ。アプリ独自の背景FPS抑制はない。最小化時のドライバー／OSの挙動は未確認。
- 推奨は起動前から有効な通常60fpsの明示上限。背景時は15〜30fpsを候補にする。内部時間を止めるかは別仕様であり、負荷対策として勝手にゲーム進行を止めない。今回は設定変更・配布をしていない。
- `world.gd:26` のDT=0.25秒、`main.gd:1628` の時間積算からWorld.stepを実行するため、「1描画フレーム=1ゲームtick」ではない。ただしdeltaを0.1秒へ制限するので、10fps未満の長い遅延では実時間に追いつかない。休息時間送り24倍では1フレームに複数stepが集中し得る。背景上限と時間送りは組み合わせて検証する必要がある。

## 3. 蓄積リスクと不要な処理

### 優先度：高

1. **セッション内の履歴が無制限。** `world.gd` のactions、job_log、combat_log、life_log、shop_log、milestones、traces、keeper_path、個体pathに、日次処理での打切りがない。tracesは8tickごと、つまりゲーム時間2秒ごとに1行。通常速度でゲーム時間1時間なら1,800行。建築100件を登録・取消するだけでもjob_logは原則200行増える。100件は現在の予約数の上限であり、累積履歴の上限ではない。
2. **終了済みの敵を保持し続ける。** doneになるがenemies配列から退役させる処理が見当たらない。`world.gd:1127,1160`、`main.gd:1692,1760` は履歴込みで全件反復。さらにsmooth_actor内で同じ敵配列を検索する（1777行）ので、累積敵数Eに対して描画準備にO(E²)の部分がある。敵ID別RNG、姿勢・位置辞書も同一セッション内に残る。蘇生可能死体、残留敵、報酬判定は維持し、完全終了した個体だけを集約記録へ移す設計が必要。
3. **建築・解体の繰り返しで表示辞書が増える。** structure_views／gate_viewsは建物IDごとに追加されるが、撤去時のeraseがなくreset_viewまで残る（main.gd:1839）。新規開始ではclearされるためプロセス永続リークと同一視しないが、長い1プレイでの不要保持はある。
4. **履歴の単純な切捨ては危険。** seen_jobs／seen_combat／seen_skills等が配列添字をカーソルとしている。既存のskill_logはbark追加時のみ64件へ1行削除し、他のSkill追加では共通上限になっていない。barkだけで64件に達した後は、sizeが変わらずseen_skillsが次イベントを読めない経路もある。イベント連番＋読み取りカーソルを導入してからリングバッファ化する。報酬・成長・図鑑記録などゲームに必要な状態と観察履歴を分離する。

### 優先度：中

- **毎フレームの全体走査・一時配列生成。** main.gdは主画面／HUD／overlayを毎フレーム再描画。scene_actorsは全木・岩・建物等を辞書配列へ展開してから可視判定・ソート。retained_groundは毎フレーム構造物等のhashを計算。view外の描画は減るが、CPU走査は全域分残る。一時配列は参照終了で解放可能であり、これ自体をリークとは扱わない。
- **画像取得の反復。** ui_assets.portrait、market_view.art_texture、merchant_speech.mouth_rect、progression_art.bounds、six_motion.bounds、main.enemy_boundsにget_image().get_used_rect()がある。通常描画／選択で繰り返し到達可能。画像取得・領域走査を素材別にキャッシュする余地がある。GPU同期やメモリ帯域への実際の影響は未測定。AdoptedArt.boundsと市場商品画像の一部は既にキャッシュ済み。
- **図鑑。** book_viewは1024×640のSubViewportを2枚保持し、閉じている間は描画停止。開いている間は次ページも含め常時更新する。静止ページの変更時更新へ削減可能。RGBA8の色面だけなら合計5MiB相当だが、実VRAMは形式・追加バッファ・エンジン実装次第であり、この計算値をVRAM実測値にしない。
- **地形キャッシュ。** 100×68、8×8チャンクなので117区画（Base＋Chunkの234ノード）。地面6800セル・メッシュを再利用し、世界変更時に旧チャンクqueue_freeと辞書clearがある。隠れたチャンクは保持する設計で、スクロールするたび新しい世界が無限保存される構造ではない。Board／Rock／StoryViewのstatic参照は最後に使ったWorldを保持するので、破棄境界は明示する余地がある。旧新Worldの切替フレームに一時共存し得る。
- forest_pattern.cacheはseedごとにFastNoiseLiteを保持し削除がない。ただしtree()の現行呼出しは旧地形互換経路で、新規バイオーム生成が必ず使うものではない。現行通常プレイでseedごとに増えると断定しない。

## 4. 診断撤去・ディスクへの蓄積

`caf02f8`でF9診断、play_diagnostics、比較シェーダー、診断起動スクリプトを削除。現行通常ロード・main・起動スクリプトにも参照なし。terrain_metricsはenabled=falseの既存計数器で、ファイル書込みはない。

完全に計測処理がゼロではない。mainのdraw_profileは毎描画で3種類の時間を上書きし、loading.timingsも少数値を保持する。履歴配列・定期ファイル出力ではない。F8の観察JSON手動出力は残り、world.observationで履歴を複製して同期JSON化し、observations/latest.jsonへ上書きする。ファイル件数は増えないがサイズ上限がなく、長時間後にはRAMの一時ピーク・停止時間を増やす可能性がある。

セーブ／ロード／自動保存は通常メニュー・起動経路から外れている。morning_save／research_snapshotと旧テスト用コードは残るが、存在だけを通常保存の再稼働と扱わない。旧history・snapshot・観察原本は保持。Godot標準ログの実効ローテーション上限、ドライバー側キャッシュ、OSによるI/Oは未測定・未確定。

## 5. 大量建築と大規模化

前回の[REPORT.md](REPORT.md)／[before.json](before.json)／[after.json](after.json)の再利用。100×68・seed731・空地・無限素材fixture・headless・30fps制限・直列。値は関数呼出しの経過時間で、フレーム時間、CPU使用率、RAMピークではない。今回の追加実行なし。

|---:|---:|---:|---:|---:|---:|
|10|158.20→0.26|314.15→0.56|7.50|43.86|78.49|
|50|783.30→1.17|1575.71→2.76|5.46|28.24|68.13|

100候補の屋内探索679,900セル→100セル。同じドラッグ再評価は候補検査0回。100仕事・10人では6,493,045セル→955セル。選択1,000対象・20更新の中央値170.33→18.12ms。以前の大量建築停止の主因は候補ごとの全域屋内探索と重複した評価。PC全体フリーズの原因とは別。

N=セル数、J=仕事数、H=住人数、S=状態キーのデータ量、V=可視物数、E=累積敵数。

- 予約索引は平均O(J＋追加数)、現在の仕事データはO(J)、追加・取消の履歴は累積操作回数に比例。J=100に制限しても履歴は抑えられない。
- 単位コストの仕事距離評価はO(H×(N＋J log J))が目安。閉ドアがある場合の既存A*はfrontier線形探索等で最悪O(N²)。実歩行と資材搬入候補の経路探索は別途残る。
- 屋内判定は局所化したが、全域舗装などでは動物ごとにNまで広がり得る。10人同時仕事評価114.86msは60fpsの16.67ms予算を超える。住人ごとの評価の分散と変更通知が次の課題。
- プレビュー状態hashはO(S)。個体pathや終了敵もhash対象なので、履歴蓄積が建築プレビューにも波及し得る。
- scene_actorsは全対象の走査＋O(V log V)ソート、敵平滑化にはO(E²)。画面外の建物が増えてもCPU走査が増える。
- 地形キャッシュRAMは概ねO(N)、個体／仕事はO(H＋J)、履歴はプレイ時間・操作回数に比例。テクスチャは多くが共有素材なので住人10人で単純にVRAM10倍にはならない。GPUは可視面積・重なり・ドローコールに依存し、使用率・必要VRAMの数値予測は今回しない。
- 資源スタックは現物ゲーム状態なので削除不可。未回収資源が増えると検索・物流評価も増える。数量の正確さを維持して座標／種類索引を作る必要がある。

## 6. 改修の優先順

1. 通常60fpsを明示し、背景時の上限を分ける。ローディング開始前から適用。低FPS時の時間積算を検証してから配布。
2. 履歴を連番付き容量制限へ移行。必要な実績・報酬状態は独立保存し、演出の取りこぼしを防ぐ。F8出力にも行数／容量上限を設ける。
3. 終了敵をactive/corpse/archiveへ分離。報酬精算・蘇生期限終了を確認して退役し、ID索引で描画の二重走査を除去。建物／個体表示辞書の退役処理を共通化。
4. 動的な有効領域矩形の画像取得を素材単位でキャッシュ。図鑑静止ページの変更時更新、静的描画の空間索引を導入。
5. 住人評価のフレーム予算化、経路探索の優先キュー化、地形／物資更新の版番号化。優先度・同点順・占有・動物屋内制限を同値テストで保持。

この監査では上記を未検証のままゲームへ適用していない。性能改善ソースe4e406aも通常EXE未反映。

## 7. 承認後に行う安全な実測計画（未実施）

最初はGPUを使わない短時間のロジック計測だけとする。以下の内容を承認されるまで起動しない。

- 1プロセス、headless＋Dummy音声、30fps上限、BelowNormal優先度。ゲームmainシーンはロードせずモデルfixtureだけ。通常EXE・APPDATA・既存セーブは使用しない。

- CPU累積時間差からプロセスCPU%、Working Set／Private Bytes、スレッド／ハンドル数、プロセスI/Oを1秒間隔で取得。OSから取得不能な値は未測定。Godot管理メモリ・Object/Node数、現行仕事／履歴／予約辞書の件数を同時記録。ログはメモリ蓄積→終了時1ファイルに限定。

- GPU、VRAM、実フレーム表示、背景時の実負荷はこの計画では未測定のまま。通常画面・高負荷GPU・無制限FPS・長時間試験は今回行わない。別途明示承認と安全な手順が整うまで実施しない。
