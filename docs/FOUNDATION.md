# WhiteSpace 基盤方針

WhiteSpaceは、ゲーム・小説・映像・ARG・仮想現実・Webなど、媒体を限定せず作品や実験を生み出す制作母体である。

この文書には、個別作品の仕様ではなく、WhiteSpace全体で繰り返し使う判断基準を置く。

## 1. 媒体より先に核を置く

先に「ゲームを作る」「小説を書く」と決めるのではなく、扱いたい観念・感情・体験・問いを見つけ、それに合う形式を選ぶ。

- 制作途中で媒体を変えてよい。
- 複数の媒体を混ぜてよい。
- 小さな試作から、核が本当に機能するか確かめる。
- WhiteSpaceは完成形式ではなく、まだ形式を持たないものに形式を与える場所とする。

## 2. 複数の独立プロジェクトを持つ

WhiteSpaceは単一作品ではない。各作品・実験を `projects/` 配下の独立プロジェクトとして扱う。

当面は一つのリポジトリで管理する。ただし、本制作・公開・保守へ進み、独自の依存関係、CI、権限、ブランド管理が必要になった場合は、そのプロジェクトだけ別リポジトリへ切り出す。

一般向けを含む作品はWhiteSpace名義を基本とする。成人向けなど明確な分離が必要になった場合は、BlackSpace（仮）など別ブランドを検討する。

ブランド名と、法的な会社名・販売者名は別の問題として扱い、公開時に必要になった段階で整理する。

## 3. プロジェクト開始時に方針を定義する

各プロジェクトは、少なくとも次を最初に短く定義する。

- 何を作る／何を確かめるプロジェクトか
- 作品または実験の核となる問い
- 完了または区切りをどう判断するか
- AI/Codexへどこまで任せるか
- 人間だけが行う判断は何か
- 公開を目指すか、研究・試作で終えてよいか

途中で変更してよいが、変更した事実は `PROJECT_STATE.md` に残す。

## 4. 自律度はプロジェクトごとに選ぶ

すべてのプロジェクトを同じ進め方にしない。人間主導、共同制作、Codex自律駆動、ほぼ完全自律型など、その実験に合う自律度を選ぶ。

### ほぼ完全自律型プロジェクト

創作工程そのものを研究対象にする場合、プロジェクトを次のように定義できる。

> このプロジェクトは、問いの展開、案の生成、批評、選別、改稿、検証をAIエージェント群が反復する、ほぼ完全自律型の創作実験として運用する。

この方式では、人間は毎回の採用・棄却を行わず、最初に目的、制約、停止条件、権限境界を定める。AI側は複数の生成役・批評役・異質な案を保存する役を分け、一つの総合点だけで候補を消さない。

ただし、現在のAIは傑作を生成する可能性があっても、それを傑作として安定して発見・選別できるとは限らない。この不確実性も失敗ではなく、実験結果として記録する。

契約、支払い、公開操作、権利上の重大判断、不可逆な削除などは、人間の明示判断を必要とする。

## 5. AIは制作だけでなく探索にも使う

AIは完成品を一発で出す機械ではなく、可能性を大量に発生させ、変奏・批評・検証するために使う。

作品ごとの具体的な方法と実例は [Creative Methods](creative/CREATIVE_METHODS.md) に蓄積する。基盤方針と個別ノウハウを混ぜない。

## 6. 文書は少なく、役割を分ける

- ルート `README.md`: 初めて見る人の入口
- `docs/FOUNDATION.md`: WhiteSpace全体の基盤方針
- ルート `PROJECT_STATE.md`: 全体の現在地と次の判断
- `docs/creative/CREATIVE_METHODS.md`: 再利用できる創作ノウハウ
- `docs/roadmap/`: 全作品に共通する将来工程
- `projects/`: 各作品の仕様、状態、タスク、実装

同じ説明を複数文書へ複製しない。新規文書は、既存文書に自然に統合できない場合だけ作る。

## 7. 速く試し、戻れる状態を保つ

- 小さく可逆な変更はAI/Codexが進める。
- 自動テスト、lint、build、実動作確認を可能な範囲で整える。
- 仕様変更を前提にし、早期の過剰設計を避ける。
- 人間には、細かな作業経過より判断が必要な点と結果を簡潔に共有する。
- 重要な変更はGitに残し、失敗から戻れる状態を保つ。
