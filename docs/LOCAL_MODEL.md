## このworktreeで起動

モデルとランタイムはルートの `.local-llm/` に配置済みでGit対象外。他のcheckoutには自動で共有しない。[Windows公式手順](https://docs.ollama.com/windows) と [API仕様](https://docs.ollama.com/api/chat) を参照した。

1つ目のPowerShell（アプリフォルダ）:

```powershell
cd prototypes/001-nadameyo
./start-local-model.ps1
```

2つ目のPowerShell（同じアプリフォルダ）:

```powershell
npm.cmd ci
npm.cmd run dev -- --host 127.0.0.1 --port 5174 --strictPort
```

[比較ラボ](http://127.0.0.1:5174/#compare) を開く。各サーバーはCtrl+Cで停止。スクリプトは `OLLAMA_HOST=127.0.0.1:11435`、モデル保存先をworktree内に固定し、`OLLAMA_NO_CLOUD=1`、並列1・ロードモデル1に設定する。自動起動サービスは登録していない。

新環境では公式リリースの `ollama-windows-amd64.zip` と `sha256sum.txt` を取得し、SHA256照合後、`.local-llm/ollama/ollama.exe` になるよう展開する。サーバーを上の手順で起動してから、別PowerShellで次を実行する。

```powershell
./start-local-model.ps1 -Pull
Invoke-RestMethod http://127.0.0.1:11435/api/tags
```

タグ・digest・サイズを上記と比較する。スクリプト自体はモデルを自動取得しない。Vite previewでもAPIは動くが、distだけを静的配信した場合は辞書のみ利用可能。

## 再測定

アプリフォルダから `npm.cmd run compare:language`。対象モデルを一度アンロードし、28例を逐次評価後、c01を再送する。他の比較処理を止めて実行する。現在のスクリプトは `docs/experiments/language-comparison-2026-09-06.json` を上書きするので、別条件の実験は先に出力名を変更する。

同一の実装・入力を使い、期待値はモデルへ渡さない。温度0、seed42、コンテキスト4096、最大生成220トークン、think=false、JSON schema指定。seedを固定しても環境間の完全な再現性は保証しない。

| 測定（最終保存JSON） | 時間 |
| --- | ---: |
| 明示アンロード後、最初のc01（形式不正応答） | 4,867.4 ms |
| その内訳: モデル読込 / 推論 | 3,932.1 / 925.5 ms |
| 読込後28呼出しの中央値（形式不正も含む） | 614.4 ms |
| 同最小〜最大 | 501.9〜899.1 ms |
| c01のウォーム再送（形式不正応答） | 859.9 ms、読込1.5 ms |
| 辞書28例の中央値 / 最大（Node実行） | 0.072 / 0.572 ms |

これはモデルをアンロードした測定であり、OSキャッシュやCUDA初期化まで完全に冷えた状態ではない。最初の環境立ち上げ時には30秒制限で2回タイムアウトし、初回初期化の完了時間を測れなかった。初回試行は `language-comparison-initial-attempt.json` に別保存し、最終測定と混ぜて集計していない。観察を受け、サーバー待機上限を120秒に変更した。

有効形式17/28、形式不正11/28。形式が有効でも正解ではない。評価結果・誤解例は 本書末尾の誤解例、応答原文と時間は [実測JSON](experiments/language-comparison-2026-09-06.json)。入力はレビュー例と生成例で、実プレイヤーのログではない。

## コーヒー自由入力の実測（2026-09-10）

既存 **Ollama 0.33.3 / qwen3.5:2b-q4_K_M（約1.945GB）** を使用。新モデル・依存の追加取得なし。127.0.0.1:11435のみ、クラウド無効。今回の起動ログでもRTX4070 SUPER/CUDA利用を確認。環境の詳細は本書冒頭を参照。

入力280文字、主人公の既知情報、直近5往復だけを渡す。未開示の希望・原因を送らない。出力はstatus/act/target/evidence/reasonの5項目。型・許可行為と対象・保留の整合・入力内に実在する根拠を検証する。モデルは物/数値を指定できない。温度0、seed42、think=false、4096 context、最大300生成トークン。

解釈が有効でもプレイヤーが「この解釈で進める」を押すまで状態は変えない。未対応/保留は聞き返しとして残せる。不正形式は適用しない。45秒サーバータイムアウト・50秒ブラウザ待機上限・中止・通信失敗を扱い、選択肢は常に使える。条件変更や選択肢操作で進行中の推論を中止し、遅れて来た結果を捨てる。Enterは改行で、送信ボタンを使う。

生成した10例（実プレイヤー入力ではない）を2版のプロンプトで実測した。期待行為は暫定でモデルへ送っていない。

- [v1実測](experiments/coffee-language-2026-09-10.json)：最初の要求は45秒でタイムアウト。完了した9例中3例のみ形式有効。相手の同意の不明を「発言の意味が不明」と取り違え、保留と具体的対象を混在させた。
- v2では「実行可否でなく発言の行為を読む」と明示し、謝罪/保留の短い出力例を追加。[v2実測](experiments/coffee-language-v2-2026-09-10.json)：10例中9例形式有効、2例が謝罪、7例が保留、1例が形式不正。形式有効を意味正解と同一視しない。
- v2の有効9応答：中央値 **0.344秒**、範囲 **0.269〜8.148秒**。モデル読込欄は約1.5〜2.1msで、すでにロード済み。Cの8.148秒は外れ値として残す。コールド読み込みの完了時間は測れていない。
- A/Cの「ごめん」はモデルが同じapologizeを返し、アプリが責任の違いから別の反応を選べた。
- 「ティッシュ、使いますか？」「ティッシュを渡す」「さっき何があったって？」は過剰に保留。否定は肯定行為へ強制されなかったが理由は不適切。「店員を呼んで」も未対応と正しく区別できない。「ごめん、ティッシュいる？」は形式不正。

現状の自由入力は確認付き実験。選択肢の代替として安定した完成度ではない。次に試すなら、同意・実行可否と発言の解釈をさらに切り離した少数例と未使用の言い換えで比較する。今回の測定例への過適合に注意する。

## 言語比較で観察した誤解（2026-09-06）

Qwen3.5のQ4_K_M版をこのPCのOllama/CUDAで実行した。28例はレビュー3例＋生成25例。モデル未実行の結果をモックや辞書結果で埋めていない。モックは自動テストだけに使用。

| 入力 | 辞書 | モデル | 観察 |
| --- | --- | --- | --- |
| 気持ちがまとまるまで待つよ | 未分類 | 安心 | 辞書にない猶予の言い換えを拾った |
| 君を傷つけたことを反省している | 未分類 | 謝罪 | 反省の意味を拾った |
| あなたは一人じゃありません | 未分類 | 安心 | 丁寧形の言い換えを拾った |
| ごめん、話を聞くよ | 傾聴 | 安心 | 指定した代表カテゴリ優先順位に反した |
| 最後まで耳を傾けるよ | 傾聴 | 安心 | 傾聴を安心へ広げすぎた |
| 明日雨が降るかもしれない | 未分類 | 安心 | 入力にない相手の不安を推測した |
| ごめん、嘘つき | 保留 | 謝罪 | 肯定と敵意の混在を見落とした |
| 大丈夫じゃありません | 保留 | 形式不正 | rejectionとuncertainを同時出力。理由にも意味の混乱がある |

28例のうち17例が形式検証を通り、11例は不正として判定に不採用。有効形式の10例で辞書とカテゴリ/保留状態が異なる（優劣や正答率を意味しない）。LLMをゲーム標準へ採用する根拠は不足。まず固定モデルのまま出力形式とプロンプトを小さく改善し、別の未使用ケースで確かめるのが次の実験。

最終保存のアンロード後初回は4.867秒（読込3.932秒）、ウォーム中央値0.614秒。初回環境初期化は30秒制限に2回達して全時間未測定。測定条件は本書の「再測定」を参照。



補足のブラウザ実測（主集計と混ぜない）：2026-09-06のproduction previewで「ごめん」は辞書/モデルとも謝罪、モデル528.9ms。2026-09-10のコーヒーC「ごめん」は0.24秒、採用前に履歴0件・採用後に謝罪反応、形式不正の混在入力では履歴1件を維持した。

コーヒーを再測定する場合はアプリ内で `node scripts/measure-coffee.mjs ../../docs/experiments/新しい出力名.json`。省略すると既存v2実測を上書きするため、必ず別名を指定する。これは新しい測定の手順であり、文書整理時に再実行したという意味ではない。
